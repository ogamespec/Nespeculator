# 04-ppu-overview — PPU architecture, internal buses, revisions

**Status:** consensus (round 2)
**Scope:** The RP2C02 / RP2C07 Picture Processing Unit as a chip: its block
diagram, the three internal data buses (DB, PD, OB) and their open-bus
semantics, the CPU-side interface pins and the internal 0–7 register index, and
the differences between the commercial and arcade revisions (2C02A…H,
2C03/2C04/2C05, 2C07, UMC 6538). Register bit fields and their side effects are
in `04-ppu-registers.md`; the VRAM address space and the rendering pipeline are
in `04-ppu-memory-map.md` and `04-ppu-rendering.md`.
**Primary sources:** `BreakingNESWiki/PPU/Readme.md`, `regs.md`, `pads.md`,
`fsm.md`, `mux.md`, `hv.md`, `pclk.md`, `visual2c02.md`, `umc6538.md`,
`rgb.md`, `rails.md`, `BreakingNESWiki/Ricoh.md`;
`Docs/NES_Famicom_Board_Revisions.md`; HDL `HDL/PPU/ppu_top.v`, `pads.v`,
`regs.v`, `fsm.v`, `hv.v`, `pclk.v`; NESdev `PPU`, `PPU_variants` (standalone

Machine).

## 1. The chip

The PPU (Picture Processing Unit) is a Ricoh `RP2C02` (NTSC) or `RP2C07` (PAL)
video generator. It is a *semi-analog* part: its `VOUT` pin (pin 21) already
carries the finished composite video signal, generated by an on-chip
current-summing DAC from the 6-bit palette entry (`PPU/Readme.md`,
`PPU/pads.md`). The RGB parts (2C03/2C04/2C05) replace pins 14–17 and 21 with
`RED`, `GREEN`, `BLUE`, `AGND` and `/SYNC` (pin 21) and use an RGB encoder
instead (`PPU/rgb.md`).

Clock and region:

| Region | Part | Master clock `CLK` | Dot clock `PCLK` | Frame geometry |
|---|---|---|---|---|
| NTSC | RP2C02 | 21.477272 MHz | 21.477272 / 4 = 5.369318 MHz | 262 scanlines × 341 dots |
| PAL | RP2C07 | 26.601712 MHz | 26.601712 / 5 = 5.3203424 MHz | 312 scanlines × 341 dots |
| Dendy famiclone | UMC UA6538 (RP2C07 clone) | PAL video clock | 5.3203424 MHz | 312 scanlines of 341 dots; 50 post-render scanlines instead of 1; `/VSET` 50 scanlines later than 2C07 |

On a Dendy the PPU runs at PAL rates while the CPU runs at nearly the NTSC
frequency, which makes PAL games run fast and causes flicker/hangs
(`BreakingNESWiki/Dendy.md`).

`CLK` is divided by four (NTSC) or five (PAL) with a dynamic-latch divider to
produce `PCLK`; `CLK` itself runs only the video phase generator, every other
block being clocked by `PCLK` / `/PCLK` (`PPU/pclk.md`). One `PCLK` period is one
dot = one pixel. The PPU is not the CPU's slave: the CPU interface is
asynchronous to `PCLK` (`PPU/regs.md`).

The only dedicated control line the PPU sends to the CPU is `/INT` (pin 19),
wired on the console to the CPU `/NMI`; it is asserted at the start of vblank by
the `INT_FF` latch inside the H/V FSM and is cleared by `RESCL` (the vblank-end
event) or by a `PPUSTATUS ($2002)` read (`PPU/fsm.md`, `PPU/pads.md`). The PPU
also drives D0–D7 while a readable register is selected.

## 3. Internal data buses

| Bus | Abbrev. | Master | Users |
|---|---|---|---|
| CPU data bus | DB | PPU Regs | PatGen, OAM Ctr, OAM Buffer, Ctr Regs, Color Buffer, Read Buffer, Strike Test, Interrupt Ctr |
| PPU data bus | PD | NT RAM, CHR ROM, `$2007` | PatGen, BGCOL, H. INV |
| Object bus | OB | OAM Buffer | PatGen, Obj FIFO, OAM Eval |

(Source: `PPU/Readme.md` §"Шины PPU".) In NESdev terms DB is the *PPU I/O bus*
(the "PPUGenLatch" of FCEUX), PD is the *video memory data bus*, and OB is the
sprite/OAM bus.

- **DB is capacitive.** A value written by the CPU is placed on DB and stays
  there after the interface releases the bus (`/DBE = 1`); internal PPU logic
  may latch it only later, and NESdev adds that the value begins to decay after
  a frame or so once the PPU is warm. This matters most for `$2003` and `$2007`.
  An HDL implementation MUST model DB as a transparent latch / bus keeper, not
  as a wire that goes to `z` (`PPU/Readme.md`; NESdev `PPU_registers`). Reading
  any nominally write-only register returns the last value on DB — see
  `04-ppu-registers.md` §4.
- **PD floats less.** PD is multiplexed with the `PA` (PPU address) bus, so a
  read of an address with no memory connected normally returns the low address
  byte rather than a decaying latch (`PPU/Readme.md`, `PPU/pads.md`).
- **OB is a push bus.** OAM Buffer drives OB for sprite pattern fetch, sprite
  evaluation and the Object FIFO (`PPU/oam.md`, `HDL/PPU/ppu_top.v`).

## 4. CPU interface

| Pin | No. | Dir | Function |
|---|---|---|---|
| `R/W` | 1 | in | Read-notWrite: 1 = read, 0 = write |
| `D0–D7` | 2–9 | bidir | Register data; driven only while `/DBE = 0` |
| `RS0–RS2` | 10–12 | in | Register select — the NESdev `A2–A0` pins, internal index 0–7 |
| `/DBE` | 13 | in | Data bus enable (NESdev `/CS`); 0 = CPU interface active |
| `EXT0–EXT3` | 14–17 | bidir | Colour in/out to another PPU; direction from `$2000[6]` |
| `CLK` | 18 | in | Master clock |
| `/INT` | 19 | out | VBlank interrupt |
| `VOUT` | 21 | out | Composite video |
| `/RES` | 22 | in | Reset (NESdev `/RST`) |
| `/WR` | 23 | out | VRAM write strobe |
| `/RD` | 24 | out | VRAM read strobe |
| `A8–A13` | 25–30 | out | VRAM address high bits |
| `AD0–AD7` | 31–38 | bidir | Multiplexed VRAM address/data; `ALE = 1` selects address |
| `ALE` | 39 | out | Address latch enable |

(Source: `PPU/pads.md`; NESdev `PPU_pinout` supplies pin 20 = GND and pin 40 =
+5V, which `PPU/pads.md` omits.)

The `R/W` decoder produces two complementary internal strobes that drive the
D0–D7 pads only — `HDL/PPU/ppu_top.v` names them `n_CpuRD`/`n_CpuWR` and routes
them to `pads.v`, not to the VRAM pins (`PPU/regs.md` §"R/W Декодер",
`HDL/PPU/regs.v` `RWDecoder`):

| `R/W` | `/DBE` | `/RD_CPU` | `/WR_CPU` | Meaning |
|---|---|---|---|---|
| 1 | 0 | 0 | 1 | read, CPU interface enabled |
| 0 | 0 | 1 | 0 | write, CPU interface enabled |
| x | 1 | 1 | 1 | interface disconnected (neither read nor write) |

Register select decodes `RS0–RS2` and `R/W` into one active-low strobe per
operation. `$2005`/`$2006` are further split into first/second pulses by the
shared write latch (see `04-ppu-registers.md` §7); `$2004` has both a read and a
write strobe (`PPU/regs.md`, `PPU/rails.md`, `HDL/PPU/regs.v`).

## 5. Register indices and the `$2000–$2007` mapping

Only eight registers are addressable inside the PPU; the `$2000`-based names
are produced *outside* the PPU by the console's address decoder
(`PPU/regs.md`). The R/W decoder and register select are not clocked by `PCLK`,
so a programmer may write registers at any dot, including in the middle of
rendering (`PPU/regs.md`).

| State of `RS2..RS0` | Internal index | CPU address | Access | Internal strobe |
|---|---|---|---|---|
| %000 | 0 | `$2000` | write | `/W0` |
| %001 | 1 | `$2001` | write | `/W1` |
| %010 | 2 | `$2002` | read | `/R2` |
| %011 | 3 | `$2003` | write | `/W3` |
| %100 | 4 | `$2004` | read / write | `/R4`, `/W4` |
| %101 | 5 | `$2005` | write | `/W5/1`, `/W5/2` |
| %110 | 6 | `$2006` | write | `/W6/1`, `/W6/2` |
| %111 | 7 | `$2007` | read / write | `/R7`, `/W7` |

(Source: `PPU/rails.md`, `HDL/PPU/regs.v` `RegSelect`.)

The console decoder selects the PPU for `$2000–$3FFF` (`74LS139` at U3,
`Docs/NES_Famicom_Board_Revisions.md` §5.2) but does not decode `A3–A12`, so the
eight registers repeat every 8 bytes: a write to `$3456` is a write to `$2006`
(NESdev `PPU_registers`). The Wiki documents only the external `$2000` naming
and the internal 0–7 indexing (`PPU/regs.md`).

The Wiki's own names for the two control registers are `CTLR0` and `CTLR1`
(not a typo) (`PPU/regs.md`).

### 6.1 The 2C05 identifier

On the arcade RGB 2C05 series, `PPUSTATUS` bits 4–0 do not return the PPU open
bus but a constant that games use as a copy-protection check. RC2C05-01…04 also
swap the PPUCTRL and PPUMASK addresses (`PPU_variants`), though not which
register answers which address — see *Open questions*. The 2C05-99 (consumer,
Famicom Titler) is exempt: it returns open bus as usual.

| PPU | Mask applied | Expected value |
|---|---|---|
| 2C05-02 | `$3F` | `$3D` |
| 2C05-03 | `$1F` | `$1C` |
| 2C05-04 | `$1F` | `$1B` |

(Source: NESdev `PPU_registers` §"2C05 identifier"; not covered by the Breaking
NES Wiki — see *Open questions*.)

### 6.2 2C04 series

The 2C04-0003 (the only RGB die photographed here) replaces `EXT0–3`/`VOUT`
with RGB outputs and drops the OAM read (`/R4`, simpler OAM Buffer), the
palette read (simpler Color Buffer), Even/Odd and `BURST`; emphasis drives the
emphasized channel fully on (`PPU/rgb.md`).

### 6.3 UMC 6538 (Dendy)

Relative to the reference PAL `RP2C07`: the V decoder's `VPLA_4` fires 50
scanlines later, moving `/VSET` (and the vblank/NMI point); the Even/Odd OAM1
write block (scanlines 265–311) is present but disconnected; the DAC is
redesigned and brighter; optional latches were added on `OAM8` and `/PICTURE`
(`PPU/umc6538.md`). Because the Dendy CPU is faster than the PPU expects
(`BreakingNESWiki/Dendy.md`), software relying on the 2C07's frame length or
vblank line behaves differently there.

## 7. Reset

`/RES = 0` sets a reset latch whose output `RC` ("Registers Clear") clears the
PPU registers (`PPU/pads.md`). The FSM also contains `INT_FF`, the vblank
interrupt latch; `RESCL` (the vblank-end event, also called `VCLR`) or a
`PPUSTATUS` read clears it (`PPU/fsm.md`).

Power-on state (NTSC measurements, NESdev `PPU_power_up_state`; the Wiki does
not state initial values):

| Item | At power-on | After reset |
|---|---|---|
| PPUCTRL `$2000`, PPUMASK `$2001` | `$00` | `$00` |
| PPUSTATUS `$2002` | bit 7 random | `U??x xxxx` |
| OAMADDR `$2003` | `$00` | unchanged |
| `$2005`/`$2006` write latch | cleared | cleared |
| fine X `x` | `$00` | `$00` |
| t (scroll/address preload) | `$0000` | `$0000` |
| v (current VRAM address) | unspecified | unchanged |
| `$2007` read buffer | `$00` | `$00` |
| OAM, palette, nametables, CHR | unspecified | unchanged |

Writes to `$2000`, `$2001`, `$2005` and `$2006` are ignored for ~29658 NTSC CPU
cycles after reset (≈33132 PAL), while `$2002`, `$2003`, `$2004`, `$2007` and
`OAMDMA` work immediately (NESdev `PPU_power_up_state`). NESdev attributes this
to the internal reset signal: raised at reset, released by the same vblank-end
event (`RESCL`) that clears the vblank, sprite 0 and overflow flags, so a write
landing during the clear has no effect.

## Observable phenomena

| # | Phenomenon (how it shows up) | Cause | What to do |
|---|---|---|---|
| 1 | Reading a write-only PPU register returns stale data, not `$00` | DB is a capacitive bus; reads leave the undriven bits at the last value written | Model PPU open bus as an 8-bit latch on DB, updated by every write and by `$2002`/`$2004`/`$2007` reads |
| 2 | Register writes take effect at any point in a scanline | The CPU interface is asynchronous to `PCLK`; there is no wait state | Allow mid-scanline writes; do not queue them to a dot boundary |
| 3 | Writing `$2005` and then `$2006` makes the `$2006` write the *second* half of a pair | One shared first/second write latch serves both registers | Always read `$2002` (or rely on `RC`) before a `$2005`/`$2006` sequence |
| 4 | Same game produces NTSC and PAL timing differences | Frame geometry (262 vs 312 scanlines) and the emphasis bit order differ; the CPU:PPU clock ratio differs too | Branch on the region; never reuse NTSC dot counts on PAL/Dendy |
| 5 | `/INT` drops at the start of vblank and can be missed by polling | `INT_FF` is set by `/VSET` and cleared by `RESCL` or a `$2002` read | Use NMI, not `$2002[7]` polling; clear the flag before enabling NMI |
| 6 | Reading `$2004` gives garbage on an early console | OAM read (`/R4`) exists only from the 2C02G on; 2C04 RGB parts have no `/R4` at all | Gate OAMDATA reads on the revision; do not use them for sprite collision |
| 7 | A write to `$2003` silently corrupts sprites on a 2C02G | OAMADDR writes on the 2C02G copy a row of OAM from the open-bus address | Write `$00` to `$2003` and refresh all 256 bytes with OAMDMA; never do partial OAMADDR writes |
| 8 | Palette reads return a value immediately with no priming read | Palette RAM is overlaid on the VRAM space and bypasses the `$2007` read buffer | Treat `$3F00–$3FFF` reads specially; 2C02E and earlier return the shadowed VRAM instead |
| 9 | A Dendy runs PAL video but its NMI arrives at a different line than a 2C07 | UMC 6538 shifts `VPLA_4` by 50 scanlines | Use the Dendy's own vblank point; do not reuse 2C07 scanline numbers |
| 10 | Sprite pixels glitch at X=255 on very early consoles | 2C02A/B fetch bug at the end of the line | Constrain sprites away from X=255 if the target hardware is a 2C02A/B |
| 11 | The frame buffer is 262 (NTSC) or 312 (PAL/Dendy) scanlines of 341 dots | 9-bit H and V counters with FSM resets at H=340 and V=261 (NTSC) | Size the frame buffer and the dot schedule per region; the Dendy spends 50 post-render lines instead of 1 |

## Programming / implementation notes

- MUST model the three buses separately: DB (CPU-side, capacitive),
  PD (VRAM-side, multiplexed with the address bus) and OB (sprite-side).
- MUST implement DB as a transparent latch or bus keeper; reading an
  unimplemented or write-only PPU register MUST return the current DB value,
  not `$00`.
- MUST decode `RS0–RS2` into the internal index 0–7 and apply the external
  `$2000`-based naming only in the CPU address map; the PPU itself knows only
  the index.
- MUST mirror the registers every 8 bytes across `$2008–$3FFF` in the CPU
  address map.
- MUST implement one shared first/second write latch for `$2005` and `$2006`,
  cleared by `RC` (`/RES`) and by a `$2002` read.
- MUST route the R/W decoder's `/RD_CPU`/`/WR_CPU` (HDL `n_CpuRD`/`n_CpuWR`)
  only to the D0–D7 direction logic (complementary while `/DBE = 0`, both `1`
  while `/DBE = 1`); the VRAM `/RD`/`/WR` pins 24/23 come from the VRAM
  controller and stay active during rendering with `/DBE = 1` (`PPU/regs.md`
  §"R/W Декодер", `PPU/pads.md`, `PPU/vram_ctrl.md`, `HDL/PPU/ppu_top.v`).
- SHOULD drive `ALE` high for the address half of a VRAM cycle and low for the
  data half; `AD0–AD7` is bidirectional.
- MUST keep `/INT` (vblank) and the `$2002[7]` flag as one latch; asserting
  `/INT` is what produces the CPU NMI.
- MUST hold the internal register-clear signal from `/RES` until the end of
  vblank (`RESCL`), not merely for the `/RES` pulse: NESdev
  `PPU_power_up_state` states that the signal is raised at reset and released
  by the vblank-end event, and that writes landing during the clear are
  ignored. Emulators that clear only during the pulse will accept `$2000`/
  `$2001`/`$2005`/`$2006` writes about one frame too early.
- MUST make `RC` clear `$2000`, `$2001`, the scroll/address latch `t`, the fine-X
  register `x`, the write latch `w` and the `$2007` read buffer — but not `v`,
  OAM or palette RAM (NESdev `PPU_power_up_state`; `scroll_regs.v` `Fine_H`).
- MUST model the OAM refresh constraint on PAL/2C07 parts: sprite evaluation
  always runs, so OAM writes are only safe in the first 24 scanlines after the
  vblank flag is set (OAMDMA included); the Dendy UA6538 does not block those
  writes, so the same program may corrupt OAM there and not on a real 2C07.
- SHOULD make revision behaviour selectable: at minimum NTSC 2C02, PAL 2C07,
  RGB 2C03/2C04/2C05, and the UMC 6538 clone, because `/R4`, palette reads, the
  OAMADDR bug, the OAM-refresh blocking and the vblank line all differ.
- MAY ignore the `EXT0–3` dual-PPU path on a single-PPU console, but MUST NOT
  drive those pins as outputs unless `$2000[6] = 1`.

## Open questions

- **`RC` semantics.** `PPU/pads.md` describes an `/RES` latch held until
  `RESCL = 1`, implying registers stay cleared until the end of vblank;
  `HDL/PPU/pads.v` deliberately changed `RC` to `RES` (clear only during the
  reset pulse) with a comment that the latch version wiped the registers every
  frame. Which matches silicon? NESdev `PPU_power_up_state` supports the
  *held* reading in effect — it states that the internal reset signal is
  released at the end of vblank by the signal that clears the flags, and that
  writes landing during the clear are ignored — though it describes a window of
  ~29658 CPU cycles, not a permanently wiped register file. The HDL's
  `RC = RES` variant loses the ignored-write window.
- **OAMADDR corruption on the 2C02G.** The Wiki has no page describing `$2003`
  write corruption; it is documented only in
  `Docs/NES_Famicom_Board_Revisions.md` §4 and NESdev `PPU_registers` (source
  address unclear, "usually $20", taken from the CPU bus). NESdev adds that it
  is *not known* whether the bug is present in all 2C02 revisions, so key it on
  the 2C02G rather than on "any 2C02". One test ROM verdict is missing.
- **`$2004` readability.** Neither `PPU/oam.md` nor `PPU/regs.md` states which
  revisions can read OAMDATA. The claim (added on 2C02G) rests on
  `Docs/NES_Famicom_Board_Revisions.md` §4 and NESdev; the `/R4` path exists in
  the HDL because it is modelled on a 2C02G.
- **2C05 identification.** The `PPUSTATUS` bits 4–0 identifier is NESdev
  (`PPU_registers` §"2C05 identifier"), which notes that no data has been taken
  directly from the PPUs — only what arcade games expect — so §6.1 is
  **unconfirmed** by ranks 1–3. The PPUCTRL/PPUMASK swap itself is stated by
  NESdev `PPU_variants` ("PPUCTRL and PPUMASK swap locations", RC2C05-01); its
  polarity is not, and no rank 1–3 source gives one. `Cycle_reference_chart` reports the
  boards "use either the 2C03 or a 2C05 with glue logic to unswap `$2000` and
  `$2001`". Do not implement a direction without a die photo or test ROM.
- **PAL 2C07 details.** The Wiki documents only the UMC 6538 clone, not the
  reference 2C07: its 71-scanline vblank and red/green emphasis swap come from
  `Docs/NES_Famicom_Board_Revisions.md` §4 and NESdev. A 2C07 die page is missing.
- **Pins 20 and 40.** `PPU/pads.md` does not list the ground and supply pins;
  the pinout table takes them from NESdev `PPU_pinout`, which draws the
  composite part with pin 20 = GND and pin 40 = +5V. Worth a second source if
  the pin table is ever used for a board-level netlist.
- **Power-on values.** `PPU/pads.md` states the `Reset FF` is `x` at power-on;
  NESdev supplies measured initial values. Emulators should treat PPUSTATUS
  bit 7 and OAM/palette contents as unspecified rather than fixed.
- **Emphasis order on PAL/Dendy.** The bit swap is not stated by any Breaking
  NES Wiki page; NESdev `Cycle_reference_chart` ("the color emphasis bits on the PAL NES
  have their red and green bits in PPUMASK swapped") and `Errata` agree, so it
  is documented community behaviour, not a schematic finding. Confirm against a
  2C07/6538 die before calling it silicon truth (neither sentence names the 2C07).
- **HDL coverage.** RGB and clone revisions are not implemented in `HDL/PPU/`
  (only `RP2C02`/`RP2C07` macros), so §6.2/§6.3 rest on `PPU/rgb.md` and `PPU/umc6538.md`.
